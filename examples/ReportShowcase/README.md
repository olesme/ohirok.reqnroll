# Report showcase

Everything the Ohirok report can show, from real test runs. One command runs four test projects over several
simulated CI builds and renders every report that leads to:

```powershell
./examples/ReportShowcase/showcase.ps1
```

Then open `examples/ReportShowcase/output/index.html` (the folder is not tracked by git). A run takes about a minute.

## What you get

| Report | What it shows |
| --- | --- |
| **Pipeline** (`themes/<theme>/pipeline.html`) | Five builds of two test projects combined: each build and project is a top-level node, history and health across builds (stable, flaky, regressed, fixed, broken), build 4 merged with the rerun of its failed scenarios (switch the reruns on and off in the header), every status, retries, expected and allowed failures, skipped steps, soft assertions, failing hooks, screenshots, HTML, callouts, links to bugs and backlog items, custom filters. |
| **Single feature** (`themes/<theme>/single-feature.html`) | The edge case: a report with one feature. |
| **2000 tests** (`themes/<theme>/large.html`) | Four price matrices with 500 rows each, about 7% of them failing. |
| **Each build** (`runs/build-N/*.html`) | What the formatter writes during the test run itself, with the history of the builds before it. |

Every report is rendered in each built-in theme (`default`, `cucumber-green`, `cyberpunk-purple`, `midnight-blue`, `chocolate-brown`, `portal-blue`) and
in `custom` - a theme and a template of your own, loaded by file path from [`Customization/`](Customization). Each
report also has its own light/dark switch.

## The projects

| Project | Runner | Content |
| --- | --- | --- |
| `Showcase.WebShop.NUnit` | NUnit | The main suite: catalog, pricing, shipping, checkout, resilience, health across builds and a feature with every Gherkin construct. |
| `Showcase.Payments.Xunit` | xUnit v3 | A second test project of the same product: card validation, authorization with retries, 3-D Secure (pending), refunds, currencies. |
| `Showcase.SingleFeature.TUnit` | TUnit | One feature. |
| `Showcase.Large.MSTest` | MSTest | 2000 rows generated by [`tools/New-LargeSuite.ps1`](tools/New-LargeSuite.ps1); the expected values come from the specification, not from the code under test. |
| `Showcase.Domain` | - | The system under test: a small tea shop with a few realistic bugs (a discount boundary, a free-shipping threshold, rounding of a three-decimal currency, a card range that is not recognised). |
| `Showcase.Steps` | - | Step definitions and hooks shared by all four projects. |

All projects install every Ohirok plugin (see [`Showcase.props`](Showcase.props)), so the features double as usage
examples:

| To see | Look at |
| --- | --- |
| `@retry`, `#retry`, `#on:` conditions, retry hooks | `Shipping/Shipping.feature`, `Payments/Authorization.feature`, `Showcase.Steps/Hooks.cs` |
| `#xfail`, `#afail`, `#ignore`, undefined/ambiguous/pending steps, a failing hook | `Resilience/ExpectedFailures.feature` |
| `#softassert` | `Checkout/SoftAssertions.feature` |
| Screenshots, image URLs, HTML, callouts, links to bugs and backlog items | `Checkout/CheckoutEvidence.feature`, `Showcase.Steps/EvidenceSteps.cs` |
| Rules, backgrounds, outlines with several example blocks, tables, doc strings | `Gherkin/EveryGherkinConstruct.feature` |
| Custom filters, history, `pipelineRunId`, `${ENV_VAR}` in the title | `Showcase.WebShop.NUnit/reqnroll.json` |

## How the pipeline is simulated

`showcase.ps1` sets `OHIROK_SHOWCASE_BUILD` to 1..5 and runs the web shop and payments projects for each build. A few
shop services behave differently per build the way real dependencies and regressions do: the carrier and payment APIs
time out on their first call in even builds (the `@retry` scenarios recover), the carrier API is down in build 3, the
search index is rebuilt in builds 2 and 4, a stock check regresses in build 4 and recommendations are fixed in build 3.

The formatter keeps history in a file (`Ohirok.Reporting.History.FileSystem.ReqnrollPlugin`), and
`"pipelineRunId": "build-${OHIROK_SHOWCASE_BUILD}"` makes build 4's rerun of its failed scenarios merge into the same
history row instead of adding a second one.

[`Ohirok.Reporting.Combine`](../../src/Reporting/Ohirok.Reporting.Combine/README.md) then builds the pipeline report:
every build and project as its own `--name`, and build 4's rerun as a second `--ndjson` under that build's name.
